# Hermes Personal Simulated Boring-Business Output Pattern

Use this reference when a Hermes Personal Product 001 scout run has already built templates/checklists/proof maps, but the remaining blocker is buyer value clarity: a buyer still has to infer what the kit actually helps them produce.

## Trigger

Choose this pattern when:

- Product 001 has many component artifacts but no finished example output;
- adversarial or human feedback says the value is still abstract, self-referential, or two hops away from the felt pain;
- Ai-money NotebookLM grounding emphasizes that buyers pay for implementation assets, concrete proof, or a "job" rather than information;
- strategic notebooks recommend harness/evaluator improvements, but current validators are already green and the product blocker is buyer-usefulness.

## One-run move

Create one simulated, fictional, buyer-facing model output under the product workspace, for example:

```text
products/local-service-missed-call-recovery-pack/buyer-deliverables/simulated-hvac-audit-teardown-report.md
```

The example should show the completed job the product enables, not another internal explanation of the product. For the missed-call kit, strong sections are:

1. fictional local-service scenario with clear "simulated example only" status;
2. old workflow teardown;
3. exposure hypothesis using owner-provided assumptions;
4. safer first workflow such as draft / queue / approve;
5. go / measure-first / walk-away recommendation;
6. direct handling of skeptical-owner objections;
7. explicit list of claims not to make.

## Experiment contract

Treat the surface as `preview/sample`.

Good pre-public metric:

```text
objection coverage
```

Example baseline/result:

```text
baseline: 0/3 finished simulated-output objections covered
result: 3/3 objections covered: AI texting trust, existing receptionist/phone system, prior-agency skepticism; exposure framed as hypothesis
```

Ledger decision is usually `promote` if the example makes the output more concrete without changing title, price, CTA, audience, platform, public exposure, or claims.

## Safety language

Keep the artifact claim-safe:

- use fictional data only;
- call calculations "exposure hypothesis," not recovered revenue;
- avoid revenue/ROI/legal/compliance guarantees;
- state no public posting/listing/checkout/outreach/setup is approved;
- do not use private/client data as proof.

## Verification

Before committing, run the required repo validators plus a quick targeted scan/check that the simulated output includes the named objections and claim-safety framing. A simple local check can assert presence of the three objection headings and absence of hard claims like "this will recover" outside a "do not say" section.
