# JMD Visibility Durable Knowledge Closeout

Use for every active or newly created issue in the Linear **JMD Visibility** project.

## Definition of Done

Before moving an issue to Done:

1. Review the work, evidence, approvals, and decisions for durable JMD Menswear business knowledge.
2. If durable knowledge exists, update either:
   - `~/obsidian-vault/hermes-brain/wiki/consultancy/clients/JMD/Client JMD Menswear.md`; or
   - a clearly linked JMD topic page under `wiki/consultancy/clients/JMD/`.
3. Promote source-backed reusable facts only, such as:
   - stable ownership/access models;
   - approved business/commerce/content rules;
   - public-safe system identifiers;
   - canonical routes and redirect strategy;
   - analytics/reporting conventions;
   - hosting/migration architecture;
   - owner-approved decisions and reusable lessons.
4. Never store passwords, tokens, recovery codes, or secrets.
5. Keep live task status, checklists, temporary blockers, weekly/transient metrics, PR/commit details, and raw test logs in Linear, GitHub, or approved report artifacts. Obsidian is not a parallel tracker.
6. Add a Linear closeout comment naming the exact wiki path(s) and durable facts updated.
7. If nothing qualifies, state **“No durable JMD business knowledge to promote”** and explain why.
8. Verify wiki changes by reading the touched pages back; update frontmatter/index/logs when required by the Hermes Brain workflow. Do not accept an agent self-report alone.

## Project-level enforcement

The JMD Visibility project description should retain a compact version of this rule so future issues inherit the expectation. Issue bodies should still carry an explicit knowledge-closeout section when created or groomed.

## Boundary

Linear/GitHub/repo artifacts are execution truth. Hermes Brain stores durable business memory and links back to those sources; it does not mirror their task state.
